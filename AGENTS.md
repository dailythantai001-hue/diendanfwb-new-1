- Preserve the imported TanStack route tree, navigation compatibility adapter, component organization and central database router; this keeps existing screens and data ownership intact.
- Post overflow menus expose no edit entrypoint; preserve copy/delete handlers and permissions. Mobile Search attention styling is scoped to its dock icon pseudo-element, animates only opacity with reduced-motion fallback, and uses global semantic tokens so geometry and navigation remain unchanged.
- Pending review shares an authenticated server count with bounded polling and snapshots all pending IDs by keyset before sequential bulk review; conditional pending-only writes arbitrate concurrent reviewers, and only a successful rejection may delete server-read R2 references, so duplicate clicks or competing approvals cannot delete published media. R2 failures are surfaced separately; database and object deletion are not an atomic transaction.
- Keep pending-post success presentation in PostPendingCard with a cleaned-up open-state timer and callback ref; preserve the caller's post-insert success gate and avoid parent refreshes extending the notice lifetime.
- VIP restriction aliases (including CommonLockedPopup) resolve only to VipZaloScreen; preserve caller eligibility and originating mounts/body locks, while legacy gate CTA props remain inert so restrictions cannot navigate to wallet or activate access.
- Payment QR presentation must decode legacy content tokens without changing stored messages or schema, and strip malformed tokens from every text fallback to avoid leaking internal payloads.
- Level-3 IP bans are checked by a server function reading cf-connecting-ip (never a client-sent IP); failed checks return unverified and are never cached as clean.
- Post quota/fee: Supabase 1 RPC reserve_post_slot decides price/free slots and signs a one-use ticket; Supabase 3 posts trigger rejects inserts without a valid ticket, so every post insert must go through createPostCompat or insertPostWithTicket (lib/post-quota.ts).

- Second-account (Admin Panel) posts use a SB1-signed `internal` post ticket (`reserve_internal_post_ticket`) checked by the SB3 posts trigger; never bypass the trigger by client flags — keeps real-user fee/free-quota enforcement intact.
- ALBUM VIP (is_super) cards appear in the Code list only after its Code is entered (flashUnlockFn returns a locked card, no media); media opens only via superOpenFn which requires both server VIP check and the album's Code.
- Post-card styling lives in stacked CSS layers (post-system → threads-redesign → feed-threads-* → per-pass files); a new pass gets its own file under src/styles/ imported last and must beat earlier `!important` rules with equal-or-higher specificity, so card tweaks never fork the component markup.
- Mobile composer quota-warning visibility is presentation-only; preserve quota calculations, blocked submit and VIP actions. The labeled group control retains ReactionBar's existing popup handler and account-group queries; size overrides belong in the last CSS pass.
- Theme color tokens (--card, --primary, ...) are raw HSL triplets mapped via hsl(var(--x)) by Tailwind's --color-* vars; hand-written CSS must wrap them as hsl(var(--x)) (and color-mix with the wrapped value) or the declaration is silently dropped, leaving the page unstyled.
- Nearby-scan filters persist per user in SB1 table public.nearby_filters (SQL: supabase-sql/SB1/RUN_NOW_2026-10-30_nearby_filters.sql) via lib/nearby-filters-store.ts; localStorage is only a cache so settings follow the account across devices.
- Community scan pages FEMALE second accounts from SB1 profiles (account_source=internal) by keyset id; SB2 holds only service-only scan settings, per-user daily counters and per-user scan history (nearby_scan_seen: user UUID, candidate id, time — no account copies, names or media); every attempt goes through nearby_scan_attempt_candidate so history + counting stay atomic and scanned accounts never return. Validate SB1 identity/roles first; never interpret failed reads as exhaustion.
- Scan admin reads are lazy/on-demand with manual refresh, and attempt counters/rate selection are atomic SQL operations; this avoids continuous subscriptions and cross-device quota races.
- Nearby scan quota is a one-time per-account gift package enforced only in SB2 SQL (FINAL_*_scan_gift_20_v5 files; v4 lifetime and weekly v2/v3 kept only for comparison): nearby_scan_claim_gift inserts one row per user (granted_now true exactly once), attempt_candidate is the single counting path under a per-user lock with a table CHECK and increment-only trigger; pre-v5 usage is not deducted but old history still excludes candidates, there are no grant/reset paths, the gift intro animates only on a server-confirmed granted_now, and the app fails closed on any other quota reply. Deployment needs explicit approval; SQL must go live before the frontend.
- Weekly scan concurrency verification uses independent PostgreSQL sessions on a fixed disposable local socket with synthetic fixtures, never hosted credentials; this proves interleaving without writing to the existing databases.
- Scan cards live in a per-user module store (lib/nearby-scan-session.ts) so tab switches keep results and in-flight scans; after reload openCommunityScan restores today's results from SB2 nearby_scan_seen.hit plus fresh SB1 profiles. Scans require a complete SAVED config (isScanConfigComplete), checked again server-side in runCommunityScan from SB1 nearby_filters; displayed km is simulatedDistanceKm (stable per user+candidate, clamped 10–200, inside the saved range), never real location.
- Tables whose writes must always reach Supabase (e.g. nearby_filters) are listed in NEVER_GUARD in src/lib/db/missing-tables.ts; the 404 guard would otherwise fake success/null responses for them.
- Search action guards and disabled controls read the per-user scan session busy state; bound client network waits without changing the reveal animation, and position its fixed Back row using the measured header bottom to avoid shared-header or database changes. Back's scroll presentation uses a page-local data attribute, never scan-session updates, so scrolling cannot restart the scan animation.
- Mobile scan alignment occurs before the body scroll lock and restores the entry scroll position; keep this presentation helper separate from V5 counting and animation timers.
- Own-account scan history uses authenticated SB1 identity before read-only service-scoped SB2 GET/HEAD queries, descending time/UUID keyset pagination and an upper-time snapshot; preserve nullable legacy outcomes as unknown rather than inventing hits or misses.
- Scan area filter: ScanFilters.districts (empty = all) lives inside nearby_filters JSON; the district list comes from lib/scan-districts.ts keyed by the user's SB1 profile province, at most one district (empty = all), runCommunityScan rejects districts outside that province and assigns each hit a stable scanDistrictFor() area from the saved selection (profiles have no district column).
- VIP ZALO screen (VipZaloScreen) is separate from CommonLockedPopup and reads admin_site_settings key vip_zalo_v2 only (no realtime); keeps the new design editable without changing legacy lock popups.
- VIP ZALO detail tabs extend existing slides JSON with stable IDs, management names and ordered rows; retain legacy title/body/image fields, use shared detail rendering for previews, Embla for isolated horizontal gestures, and MediaService for new detail uploads so no database/schema or legacy popup changes are needed.
- VIP ZALO reminders use a user/plan/stable-benefit browser store with an isolated Admin-preview namespace; presentation-only markers require no database schema change and survive screen remounts.
- VIP ZALO international benefits resolve from intlShared or a read-only union of legacy country lists; Admin explicitly initializes the shared list, retaining intl and an exact intlLegacySnapshot in vip_zalo_v2 so adoption never overwrites country data.
- Legacy VIP presentation is reserved for VipPopupManager's explicit old-configuration preview; never import it in user restriction flows, so old Admin data remains editable without resurfacing old gates.
- Admin post deletion from the feed menu goes through adminDeletePostFn, which verifies the token with SB1 Auth and requires profiles.is_admin === true via service key before deleting only the SB3 posts row; the client-side isAdmin only toggles the button.
